# Wear OS Companion — Spec 1: Foundation (build integration)

**Date:** 2026-06-10
**Status:** Approved (design)
**Scope:** Android Wear OS companion — foundation only. Part of a multi-spec
effort to bring the Apple Watch app to Wear OS (full parity is the eventual
target).

## Context

The app has a working Apple Watch companion (Distance + wind, Score, Leaderboard,
keep-alive). We want the same on Wear OS. Unlike iOS — where `ios/` is committed
and the watch target is hand-maintained — **`android/` is gitignored and
regenerated by `expo prebuild`**, so a Wear module dropped into `android/` would
be wiped each build. The integration must therefore be reconstructable on every
prebuild.

The TS layer in `src/watch` (snapshot building, score writes, wind, leaderboard
trimming) is platform-agnostic and will be reused unchanged for Wear; only the
transport and the native watch UI differ per platform.

## Decomposition (whole effort)

1. **Spec 1 — Foundation (this doc):** an Expo config plugin that injects a
   buildable `:wear` Gradle module on prebuild; a minimal Compose scaffold that
   installs and runs on a Wear OS emulator. No data yet. *De-risks the one novel
   piece — surviving prebuild — in isolation.*
2. **Spec 2 — Data bridge:** a local Expo native module for the Wear Data Layer
   (DataClient for snapshot state, MessageClient for score writes/acks/navigate)
   + `createWearTransport()` in `src/watch/transport.ts`, reusing the existing
   snapshot/score pipeline. Round-trips a snapshot to the watch and a write back.
3. **Spec 3+ — Features:** Distance + wind/compass, Score, Leaderboard,
   Now-Playing, keep-alive (ongoing activity), tile — toward full parity.

## Goal (Spec 1)

After `expo prebuild`, the generated `android/` contains a `:wear` Gradle module
that builds an installable Wear OS APK showing a minimal Compose screen
("The Nineteenth — Wear" + a placeholder status line). Everything in `android/`
is produced by the plugin — nothing hand-edited there — and re-running prebuild
from clean reproduces it.

## Components

### 1. `wear/` — committed Wear module source

Parallel to how `watch/` holds the iOS source. Contents:
- `build.gradle.kts` — `com.android.application` + Kotlin + Compose Compiler
  plugin; `applicationId = "com.the.nineteenth.golf"` (must match the phone app
  so the Data Layer treats them as the same app in Spec 2); `minSdk 30`
  (Wear OS 3), compile/target SDK aligned with the phone module.
- `src/main/AndroidManifest.xml` — `uses-feature android.hardware.type.watch`,
  `uses-library com.google.android.wearable`, standalone metadata, a launcher
  `MainActivity`.
- `src/main/java/.../MainActivity.kt` — `ComponentActivity` hosting a Compose
  `setContent`.
- `src/main/java/.../ui/` — a Wear Compose scaffold (app name + placeholder
  "Waiting for phone…" status) using `androidx.wear.compose.material`.
- resources (theme, strings, launcher icon).

### 2. `plugins/withWearOs.js` — Expo config plugin (referenced in `app.json`)

Runs during prebuild (`@expo/config-plugins`):
- **`withDangerousMod` (android):** copy `wear/` → `android/wear/`.
- **`withSettingsGradle`:** add `include(':wear')` (idempotent).
- **Version pinning:** the `:wear` module declares its own Wear Compose / Kotlin
  compose-compiler / `play-services-wearable` versions, chosen to match the AGP
  + Kotlin the Expo template generates (verified against the generated Gradle at
  implementation time). Pinned in the module, not the app, to avoid touching the
  RN build.
- **Embedded delivery — deferred:** wiring `wearApp project(':wear')` into the
  phone module (for Play auto-delivery to a paired watch) needs matching
  applicationId + signing (EAS-credentials concern). Out of scope for Spec 1;
  emulator dev installs the wear APK directly via `adb`.
- Idempotent: guards so re-running prebuild doesn't duplicate edits.

### 3. Docs

A short "Wear OS build" note (CLAUDE.md or docs) + a memory recording the
prebuild→gradle→adb workflow and that `wear/` is the source of truth.

## Data flow

None in Spec 1 — the screen is static. Data Layer wiring is Spec 2.

## Testing (emulator-only, per constraint)

- `expo prebuild --clean -p android` regenerates `android/` with the plugin.
- `./gradlew :wear:assembleDebug` builds the Wear APK.
- Install a Wear OS system image + create an AVD (needs `cmdline-tools` +
  `sdkmanager`; not currently installed — a one-time setup), boot it.
- `adb install` the APK, launch, screenshot the scaffold.
- Re-run `expo prebuild --clean` to confirm the plugin reproduces the module.

## Risks

- **Version alignment** (highest): Wear Compose + Kotlin compose-compiler must
  match Expo's AGP/Kotlin. Resolved by reading the generated Gradle and pinning
  accordingly; the most likely source of build friction.
- **Wear emulator setup:** no system image/AVD present; installing one is a
  sizable download and a prerequisite to "seeing it run."
- **EAS/CI:** the plugin must also run in EAS prebuild; verified locally first,
  EAS confirmed when a build is run.
- **Embedded delivery/signing:** deferred; does not block emulator dev.

## Out of scope (Spec 1)

Data Layer bridge, any real UI/features, keep-alive, tile, embedded Play
delivery. All in later specs.
