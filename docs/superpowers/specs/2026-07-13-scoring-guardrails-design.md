# Scoring Guardrails — Design Spec

**Date:** 2026-07-13
**Status:** Approved (brainstorming); pending implementation plan
**Approach:** A — Map-first, characterization tests as the backbone

---

## Problem

Editing scoring functionality in this codebase is dangerous because the domain
has two overlapping blast radii:

1. **Sibling components.** There are 10+ score-card variants
   (`PlayerScoreCard`, `TeamScoreCard` ×2, `AltShotScoreCard`,
   `StrokePlayScoreCard`, `MatchPlayScorecardTable`, `TeamMatchPlayScorecardTable`,
   `ScrambleScorecardTable`, `RingerScorecard`, `QuickScorecardView`,
   `EclecticScorecardView`, …). A change intended for one card can silently
   alter another.
2. **Shared scoring math.** Canonical math lives in
   `src/services/scoring/engines/` (MatchPlay, Par, Stableford, StrokePlay,
   TeamScoring) behind a `ScoringOrchestrator`, plus shared utils
   (`scorecardCalculations`, `dailyHandicap`, `competitionPoints`, `matchMargin`,
   `subMatches`, `teamHandicap`, `leaderboardHandicaps`, `multiBallScorecard`)
   and Zustand store slices (`scorecardStore`, `scoreUpdateSlice`,
   `initializeRoundSlice`). These are imported across ~30 non-test files, so a
   change to shared math ripples into every format.

Current guardrails are thin: ~365 test files and 86 Storybook stories exist, but
there is **no CI** (`.github` does not exist). The only automated gate is a
`Stop` hook running `pnpm typecheck`. The project's memory index shows a long
tail of scorecard work that keeps re-touching these same fragile files.

### Failure modes to address (all confirmed in scope)

- **Sibling components** — editing one card silently changes another.
- **Shared scoring math** — a shared-util change quietly breaks one format.
- **Scope creep in edits** — a change meant for one screen widens its blast radius.
- **No regression signal** — nothing fails until on-device / production.

---

## Goals & non-goals

**Goals**
- Make the scoring domain's structure and behavioural contracts explicit and
  discoverable before anyone (human or Claude) edits it.
- Provide a loud, automated regression signal for scoring behaviour.
- Force a blast-radius analysis before editing shared scoring code.
- Produce a **reusable pattern** that can later be stamped onto other domains.

**Non-goals**
- Rewriting or refactoring scoring logic. We characterize what exists today.
- Building CI now (no `.github`; ships via EAS/OTA). Noted as an optional
  future layer only.
- Hard-blocking enforcement that fights offline/fast iteration. Enforcement is
  *nudge + fail-loud tests*, not a gate.

## Domain map (as-is, grounded in the tree)

```
Screens / cards (presentational)     src/components/scorecard/**, src/screens/scoring/**
        │  (must NOT re-implement math)
        ▼
Zustand store slices                 src/store/{scorecardStore,scoreUpdateSlice,initializeRoundSlice,
                                              scorecardPersistence,scorecardSyncDebounce}.ts
        ▼
Shared scoring utils                 src/utils/{scorecardCalculations,dailyHandicap,competitionPoints,
                                              matchMargin,subMatches,teamHandicap,leaderboardHandicaps,
                                              multiBallScorecard,handicapDifferential}.ts
                                     src/services/scoring/utils/{handicapUtils,leaderboardUtils,netScoreUtils}.ts
                                     src/hooks/player/playingHandicap.ts
        ▼
Scoring engines / orchestrator       src/services/scoring/ScoringOrchestrator.ts
                                     src/services/scoring/engines/{MatchPlay,Par,Stableford,StrokePlay,TeamScoring}Engine.ts
```

**Core rule the map encodes:** scoring math lives in engines + shared utils;
cards are presentational and must not re-implement math.

## Design — five layers (Approach A)

### Layer 1 — Architecture map (durable reference)

New committed doc: `docs/guides/SCORING_ARCHITECTURE.md`. Four parts:

1. **Layer diagram** — the stack above, plus the "cards are presentational" rule.
2. **Component inventory** — each card variant → the format/screen it serves and
   the shared modules it depends on.
3. **Blast-radius table** — for each shared module and engine, the list of
   consumers ("if you change X, check these Y"). Generated by grepping importers
   and kept as a checked-in table.
4. **Per-format invariants** — the behavioural contracts, each naming the file
   that owns it and the characterization test that locks it. Seed set harvested
   from code + memory notes:
   - Alt-shot **combined** = own 50% HC, net-lowest scoring.
   - Alt-shot **split** = differential total-net.
   - Four-ball (best-ball) match play — strokes allocated **relative to lowest
     handicap in the match** (`getFourBallStrokes`).
   - Singles match play — **difference method** via shared `getMatchPlayStrokes`.
   - 9-hole daily handicap is **nine-aware** (must not inflate to ~41).
   - Pickups (`strokes === 10` / PICKUP sentinel) count as **net double bogey**
     everywhere.
   - Stableford / Par leaderboards + best-ball header score off the **round
     daily handicap**.
   - Match-play concession awards the opponent only if they have a score.
   - (Confirm/extend during implementation — this list is the seed, not final.)

### Layer 2 — Characterization tests (loud tripwire)

Lock **today's** behaviour so any drift fails:

- **Golden-value tests** on engines + shared utils: table-driven fixtures per
  format (stableford, stroke, singles/four-ball match, alt-shot combined/split,
  scramble, par, ringer) asserting exact net / points / margin outputs. Mirrors
  the invariants list one-to-one.
- **Render snapshots** per card, reusing existing stories where possible, so a
  sibling-component edit that shifts an unrelated card fails loudly.
- **Gap-fill only** where coverage is missing. Deliverable includes a coverage
  checklist mapping each invariant → its locking test, so we know what is
  actually protected.

### Layer 3 — Scoring-impact agent (pre-edit analysis)

New committed subagent: `.claude/agents/scoring-impact-analyst.md`
(read-only: Grep/Glob/Read/Bash). Given a target file it returns a
**blast-radius report**:
- every importer / consumer of the file,
- whether the file is shared-math vs. leaf-presentational,
- which invariants and which characterization tests cover it,
- a test-first plan.

Output is a short structured report, never edits.

### Layer 4 — Rules that force the check

Scoped rule in this repo's `CLAUDE.md` (under a "Scoring changes" heading) and/or
`.claude/rules/scoring-guardrails.md`. Before editing anything under
`src/services/scoring`, scoring store slices, shared handicap/points/margin
utils, or `src/components/scorecard`:

1. Read `SCORING_ARCHITECTURE.md`.
2. Run `scoring-impact-analyst`.
3. State the blast radius + which characterization tests cover the change.
4. Prefer adding/asserting a test before editing shared math.

Includes the "cards are presentational — don't re-implement math" rule.

### Layer 5 — Non-blocking enforcement hooks

- **`PreToolUse`** on `Edit`/`Write` matching scoring paths → injects a reminder
  to run the analyst and confirm a covering test exists. A nudge, not a block.
- **`Stop` hook** → extend existing `pnpm typecheck` to also run the **scoring
  test subset** (scoped to `src/services/scoring`, scoring utils, and scorecard
  component tests) so a session can't quietly end with red scoring tests. Scoped
  to stay fast.
- **CI** — deferred. Noted as an optional future layer only.

---

## Reusability

Layers 1–5 form a pattern template: **map → characterization tests → impact
agent → rule → hooks**. Once proven on scoring, the same five artifacts can be
stamped onto another domain (e.g. leaderboards, sync) by swapping the
inventory/invariants. A short "how to extend this pattern" section will be
included so it is genuinely reusable, not scoring-only.

---

## Deliverables

1. `docs/guides/SCORING_ARCHITECTURE.md` (map: diagram, inventory, blast-radius
   table, invariants + coverage links).
2. Characterization test suite + invariant→test coverage checklist.
3. `.claude/agents/scoring-impact-analyst.md`.
4. `CLAUDE.md` "Scoring changes" rule section (+ optional
   `.claude/rules/scoring-guardrails.md`).
5. Hook config: `PreToolUse` nudge + extended `Stop` hook in `.claude/settings.json`.
6. "How to extend this pattern to another domain" note.

## Open questions / risks

- **Stop-hook runtime:** running the scoring subset on every `Stop` adds latency.
  Mitigation: scope the path set tightly; revisit if it becomes annoying.
- **Snapshot brittleness:** render snapshots can produce noisy churn. Mitigation:
  prefer targeted golden-value assertions for math; use snapshots mainly for
  card structure.
- **Invariant list completeness:** the seed list must be validated against code
  during implementation; missing invariants = unprotected behaviour.
- **Worktree node_modules:** per project memory, do NOT symlink `node_modules`
  into the worktree; run `pnpm install` in-worktree before running tests.
